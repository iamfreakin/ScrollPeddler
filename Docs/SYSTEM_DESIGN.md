# Scroll Peddler 시스템 설계와 구현 로드맵

이 문서는 2026-07-27 작업 트리의 C++·설정·자동화 테스트·현재 콘텐츠를 기준으로 작성한 현황 문서다. 기획 의도와 실제로 플레이 가능한 범위를 섞지 않기 위해 다음 상태를 구분한다.

| 상태 | 의미 |
|---|---|
| **구현됨** | 현재 `TechSpike` 런타임 경로에 연결되어 서버에서 실제 상태를 바꾼다. 최종 아트와 UX가 완성됐다는 의미는 아니다. |
| **기반만 있음** | 데이터 모델, 순수 판정, 복제 계약 또는 자동화 테스트는 있으나 실제 플레이 흐름·콘텐츠·UI 중 하나 이상이 연결되지 않았다. |
| **미구현** | 현재 저장소에 완결된 실행 경로가 없다. |

## 1. 현재 플레이 루프와 순서

현재 목표 루프는 다음 순서다.

1. **호스트 캠페인 준비**
   - Listen Server 호스트가 캠페인 슬롯을 불러오며, 기본 슬롯은 0번이다.
   - 슬롯이 비어 있으면 호스트 소유 캠페인을 새로 만든다.
2. **파티 구성**
   - raw IP 또는 Steam 공개 로비로 1–4인이 참가한다.
   - 현재 인원과 준비 상태가 모두 충족되어야 원정이 시작된다.
3. **계약·출정 준비**
   - 설계상 허브에서 계약을 고르고 제작·정비한 뒤 출정한다.
   - 현재 `TechSpike`에서는 선택 UI 대신 고정 스크롤 납품 계약을 런타임에 만든다.
4. **원정**
   - 서버가 시드 기반 8방 레이아웃과 회색 상자 월드를 만든다.
   - 플레이어는 이동 소음을 관리하며 아이템을 줍고, 스크롤을 보존하거나 사용하고, 위협을 피한다.
   - 일반 원정 시간은 25분이고 이후 2분의 붕괴 구간이 있다.
5. **개별 탈출 또는 실종**
   - 각 플레이어는 탈출 지점에 개별 도달해 자신의 소지품만 확정한다.
   - 제한 시간 종료, 출혈 종료 또는 해소되지 않은 연결 끊김은 `Missing`으로 정리된다.
6. **호스트 권위 정산**
   - 탈출한 플레이어의 아이템, 스크롤 납품 가치, 계약 보상, 길드 XP를 하나의 캠페인 트랜잭션으로 저장한다.
   - 같은 `RunId`를 다시 정산해도 중복 반영하지 않는다.
7. **허브 복귀**
   - 설계상 정산함 확인, 보관함 이동, 제작, 다음 계약 선택으로 순환한다.
   - 현재는 별도 허브 맵과 복귀 화면 없이 `TechSpike` 한 맵에서 정산 완료 상태까지만 확인한다.

현재 구현된 핵심 순서는 `Preparing → Expedition(25분) → Collapse(2분) → Resolution → Settlement`이다. `Normal → Injured → Down → Missing` 상태와 1·2·3회차 Down의 45·30·15초 출혈 시간, 20초 자가 치료, 개별 탈출이 연결되어 있다.

## 2. 인벤토리와 월드 아이템

### 현재 규칙

| 항목 | 현재 규칙 | 상태 |
|---|---|---|
| 손 | 1칸. 빈 인벤토리의 첫 아이템이 우선 들어간다. | **구현됨** |
| 가방 | 4칸. 숫자 1–4로 해당 가방 칸과 손을 원자적으로 교환한다. | **구현됨** |
| 재료 스택 | 최대 10개. 같은 정의·품질·오염 단계인 재료만 합친다. | **구현됨** |
| 스크롤·장비 | 인스턴스별 고유 아이템이며 스택하지 않는다. | **구현됨** |
| 대형 화물 | 손 전용이며 가방에 들어가지 않고, 운반 중 질주가 막히며 이동 속도가 72%로 감소한다. | **구현됨** |
| 복제 | 인벤토리 전체 상태와 리비전은 소유 클라이언트에게만 복제한다. | **구현됨** |
| 버리기 | `G`로 손 아이템만 버린다. 서버가 거리와 충돌을 검사하고 실패 시 인벤토리를 복원한다. | **구현됨** |

현재 자동 배치 순서는 다음과 같다.

1. 손이 비어 있으면 손에 배치한다.
2. 손이 차 있으면 완전히 합칠 수 있는 동일 재료 스택을 손, 가방 순서로 찾는다.
3. 대형 화물이 아니면 첫 번째 빈 가방 칸에 배치한다.
4. 더 이상 경로가 없으면 획득을 거부한다.

현재 월드 획득 경로는 자동 손 교체를 허용하지 않는다. 따라서 대형 화물을 주울 때 손이 차 있으면 먼저 손 아이템을 버리거나 빈 가방 칸과 교환해 손을 비워야 한다. 순수 인벤토리 상태에는 손 교체 경로가 있으나 실제 월드 획득 RPC에서는 비활성이다.

### 권위 경계

- 클라이언트는 대상 인스턴스, 요청 ID, 예상 리비전만 보낸다.
- 서버는 소유 컨트롤러, 플레이어 상태, 거리, 시야 차단, 대상 인스턴스, 월드 아이템 리비전, 인벤토리 리비전과 용량을 검사한다.
- 월드 아이템은 `Available → Claimed → Committed` 수명주기와 서버 전용 claim token을 사용한다.
- 인벤토리 반영 후 월드 claim 확정이 실패하면 인벤토리와 스크롤 원장을 되돌린다.
- 같은 요청의 재전송은 기존 결과를 반환하고, 같은 요청 ID의 다른 내용은 충돌로 거부한다.

### 아직 필요한 결정

- 재료 스택을 일부만 합치거나 나누는 기능은 없다. 전량을 합칠 수 없으면 새 칸을 사용한다.
- 드래그 앤 드롭, 스택 분할, 정렬, 비교 툴팁, 대형 화물 교체 확인창은 없다.
- 현재 HUD는 손·가방 내용을 텍스트로 보여 주지만 최종 인벤토리 위젯은 없다.
- 장비를 착용한 동안에도 원본 인벤토리 인스턴스를 점유하게 할지, 별도 장비 보관 영역으로 이동할지 최종 정책이 필요하다.

## 3. 스크롤 6계열과 독립 축

스크롤은 다음 다섯 축을 독립적으로 유지한다.

1. **기본 계열**: 무엇을 하는가
2. **각인**: 범위·지속시간·위험의 장단점을 어떻게 바꾸는가
3. **품질 D–S**: 효과 배율
4. **오염 0–100**: 오작동 확률
5. **오작동**: 무효화, 지연, 방향 전환, 추가 소음

각인을 품질·오염·오작동의 다른 이름으로 사용하지 않으며, 저장 데이터는 정의의 Stable ID와 정확한 아이템 `InstanceId`를 유지한다.

| 기본 계열 | 회색 상자 기본 효과 | 현재 연결 상태 |
|---|---|---|
| 파괴 `Ruin` | 조준 지점 주변 위협을 영구 처치하지 않고 경직·후퇴시킨다. | C++ 적용 경로 **구현됨**, 플레이 가능한 Data Asset **미구현** |
| 회복 `Restoration` | 범위 내 동료를 `Down → Injured`, `Injured → Normal`로 한 단계 회복한다. | C++ 적용 경로 **구현됨**, 플레이 가능한 Data Asset **미구현** |
| 수호 `Ward` | 일정 시간 다음 위협 공격 1회를 막고 보호를 소모한다. | C++ 적용 경로 **구현됨**, 플레이 가능한 Data Asset **미구현** |
| 이동 `Traversal` | 조준 방향으로 캐릭터를 발사한다. | C++ 적용 경로 **구현됨**, 플레이 가능한 Data Asset **미구현** |
| 계시 `Revelation` | 탐지 활성 시간을 복제한다. | 상태 타이머 **구현됨**, 실제 하이라이트·정보 표시 **미구현** |
| 공명 `Resonance` | 행동 소음을 기본의 20%로 낮추는 침묵 시간을 적용한다. | `Veil of Silence` 콘텐츠까지 **구현됨** |

서버는 인벤토리에서 실제 스크롤을 다시 조회하고 런 시드, 품질, 오염, 각인으로 결정적 결과를 계산한 뒤 정확한 인스턴스를 한 번만 소비한다. 클라이언트가 선택하는 요청 ID는 오작동 해시에 포함하지 않아 GUID 탐색으로 나쁜 결과를 피할 수 없다. 지연 오작동은 소비 후 서버 타이머로 적용하고, 추가 소음은 권위 소음 시스템으로 발행한다.

현재 콘텐츠에는 `DA_Scroll_VeilOfSilence` 한 계열과 `Amplified`, `Stable` 두 각인만 있다. 6계열용 순수 resolver와 월드 적용 코드는 마련됐지만 나머지 5계열의 Data Asset, 픽업 구성, 아이콘, VFX, SFX, 설명과 밸런스는 아직 없다.

## 4. 장비, 위협, 소음과 디렉터

### 장비

장비 런타임 모델은 `Tool`, `Protection`, `Utility` 세 슬롯을 정의한다. 장비는 정확한 인벤토리 정의·인스턴스를 참조하고, 서버가 슬롯 호환성과 최대 내구도를 결정한다. 착용, 해제, 피해, 수리, `Good/Worn/Broken`, 리비전, 요청 재전송·충돌 판정과 자동화 테스트가 있다.

그러나 이 상태는 아직 플레이어 컴포넌트, RPC, 저장·재접속 스냅샷, 제작, HUD에 연결되지 않았다. 현재 월드의 `equipment.archive_lantern`은 일반 고유 아이템으로 주워 운반할 수 있을 뿐 실제 랜턴 기능이나 착용 효과가 없다. 따라서 장비 시스템 전체 상태는 **기반만 있음**이다.

### 위협 2종

| 위협 | 실제 행동 | 상태 |
|---|---|---|
| Echo Hunter | 권위 소음을 구독하고 조사한 뒤 시야로 플레이어를 확인해 추적한다. 예고 공격이 맞으면 상태를 악화시키고 손 아이템을 떨어뜨린다. | 회색 상자 런타임 **구현됨** |
| Paper Eater | 스크롤을 일반 아이템보다 우선해 추적한다. 월드 스크롤 오염을 올리고, 재료 오염 단계를 올리며, 장비 상태를 `Good → Worn → Broken`으로 손상한다. | 회색 상자 런타임 **구현됨** |

두 위협은 영구 사망하지 않는다. 공격형 스크롤은 `Staggered → Retreating → Idle`로 밀어낼 뿐이며, 이 규칙은 데이터 검증에도 반영되어 있다.

현재 이동은 단순 직선 이동과 line trace에 기반한다. NavMesh 경로 탐색, 문 통과, 군집 회피, 애니메이션, 피격·예고 VFX/SFX, 스폰·디스폰 연출, 막힘 복구는 아직 없다.

### 소음과 위협 디렉터

- 걷기, 웅크리기, 질주, 점프, 착지, 피로, 부상 신음, 치료, 아이템 버리기, 스크롤 오작동이 서버 소음을 낸다.
- 소음 원장은 최근 이벤트 수와 수명을 제한하고 서버 시간을 강제한다.
- 디렉터는 최근 2초 소음 압력, 활성 플레이어 수, 경과 시간으로 예산을 쌓는다.
- 예산으로 30초 쿨다운의 공포 이벤트를 발생시키거나 두 위협을 교대로 추가 요청한다.
- 각 위협은 현재 최대 2개까지 존재할 수 있다.

공포 이벤트 5종의 복제 상태와 순환 선택은 있으나 대부분의 화면·음향 연출은 없다. `EquipmentAlarm`과 `ScrollSneeze`만 추가 권위 소음을 만든다. 따라서 디렉터의 판정은 **구현됨**, 공포 연출 콘텐츠는 **기반만 있음**이다.

## 5. 파티, Steam, 채팅과 투표

### 파티 규칙

- 파티 최대 인원은 4명이다.
- 모든 현재 멤버가 준비해야 출정한다.
- 원정이 시작되면 신규 참가와 초대를 잠그고, 기존 roster의 재접속만 허용한다.
- 허브에서는 호스트가 즉시 강퇴할 수 있다.
- 원정 중 강퇴는 대상자를 제외한 유권자의 엄격한 과반수 투표로 처리하며 동률은 부결이다.
- 허브 강퇴는 고정 roster 슬롯과 미완료 기록을 제거해 다른 ID가 참가할 수 있게 한다.
- 원정 중 강퇴는 roster를 유지하되 즉시 `Missing` 결과를 확정하고 재접속 기록을 삭제한다. 강퇴된 ID의 재접속은 거부한다.
- 중요 제작은 허브에서 과반수 승인을 요구할 수 있다.
- 채팅은 허브 전용, 메시지 최대 200자, 발신자별 1초 제한, 최근 32개 보관이다.

파티 상태는 always-relevant actor로 복제되고, 준비·호스트 강퇴·강퇴 투표·투표 참여는 콘솔 명령과 서버 RPC까지 연결되어 있다. HUD는 roster, 준비·연결 상태와 최근 채팅 4개를 보여 준다.

중요 제작 투표를 시작하는 플레이어 RPC와 제작 승인 결과를 Workshop에 전달하는 실행 경로는 아직 없다. 채팅 입력창과 투표 위젯도 없으므로 현재 UX는 개발자 콘솔 중심이다.

### Steam과 음성

현재 Legacy Online Subsystem Steam 경로에는 다음 기능이 있다.

- 공개 1–4인 Listen Server 로비 생성
- 공개 로비 검색, 인덱스 참가, 최저 ping Quick Play
- 빌드 ID, 규칙 버전, Hub/Expedition, 빈자리, 참가·초대 허용 metadata 검증
- 플랫폼 친구 초대 수락
- 원정 시작 시 광고·중도 참가·초대를 끄는 세션 갱신
- Steam connect string을 통한 클라이언트 travel
- raw IP `SPHost`·`SPJoin` 폴백 유지

Steam 플러그인, Steam NetDriver와 개발용 App ID 480이 설정되어 있다. `V` push-to-talk와 플레이어 mute/unmute 명령도 연결되어 있다.

아직 Steam 로비 UI, 친구에게 초대를 보내는 게임 내 UI, 실패 복구 화면, 음성 상태 표시·장치 설정, 실 Steam 계정 간 패키지 검증은 없다. 로비 음성 채팅 전용 옵션은 사용하지 않고 기존 voice 경로에 의존하므로, 음성은 **설정과 입력 기반만 있음**으로 취급한다. 호스트 이전은 MVP 범위 밖이다.

## 6. 계약, 제작, 캠페인 저장과 재접속

### 계약

정의된 계약 종류는 다음 세 가지다.

1. 계열·허용 각인·최소 품질·최대 오염·수량을 검사하는 스크롤 납품
2. 정확한 Stable ID를 검사하는 대형 화물 회수
3. 정산 후 제한 시간 안에 서버 영수증이 확정된 후속 제작

계약 판정은 탈출한 플레이어의 아이템만 사용하며, 같은 `InstanceId`나 영수증의 중복·상충 증거를 배제한다. 성공했을 때만 금화와 길드 XP를 지급한다.

현재 `TechSpike`는 B등급 이상, 오염 30 이하인 `Veil of Silence` 1개를 보존하는 고정 계약을 런타임에 만든다. 계약 선택·교체 상태와 검증기는 있으나 실제 Data Asset 목록, 계약 게시판 UI, Workshop 선택 결과를 다음 원정 GameMode에 전달하는 경로는 없다. 세 계약 중 실제 원정 정산에 연결된 것은 고정 스크롤 납품뿐이다.

### 제작

Workshop은 다음을 원자적 캠페인 트랜잭션으로 계산한다.

- 서버가 확정한 금화 비용
- 보관함 또는 정산함에서 정확한 재료 수량 차감
- 서버가 생성한 결과 아이템 추가
- 보관함이 가득 찼을 때 무제한 정산함으로 안전하게 우회
- 중요 제작의 투표 승인 요구

레시피는 8–15초 제작 시간을 정의하지만 실제 타이머·미니게임·중단·동시 사용자 작업대는 없다. 레시피 Data Asset과 제작 UI도 없으므로 현재 제작은 **권위 트랜잭션 기반만 있음**이다.

### 캠페인과 프로필 저장

| 데이터 | 현재 규칙 | 상태 |
|---|---|---|
| 호스트 캠페인 | 고정 3슬롯, 금화, 길드 XP·랭크, 보관함, 정산함 | **구현됨** |
| 보관함 | 최대 40개 슬롯 | **구현됨** |
| 정산함 | 용량 제한 없음. 탈출 아이템과 보관함 초과 제작품의 안전 목적지 | **구현됨** |
| 로컬 프로필 | 발견, 통계, 코스메틱, 설정만 저장하고 경제는 저장하지 않음 | 저장 API **구현됨**, 게임 UI 연결 **미구현** |

캠페인 저장은 임시 파일 직렬화·바이트 재검증 후 최종 파일로 교체한다. 저장 실패 시 메모리 상태도 트랜잭션 전 스냅샷으로 복원한다. `TransactionId`, `RunId`, 예상 리비전으로 중복 정산과 오래된 쓰기를 막는다. 다만 최종 파일 교체 뒤의 매체 오류나 최종 재검증 실패에 대비한 디스크 백업 복구는 아직 없어, 프로덕션 내구성 게이트로 남는다.

호스트 캠페인이 정산의 원본이다. 클라이언트의 기존 로컬 결과 저장·ACK는 보조 영수증과 telemetry이며, 실패하거나 10초 안에 도착하지 않아도 이미 확정된 호스트 캠페인 정산을 되돌리지 않는다.

### 재접속

원정 중 연결이 끊기면 호스트 메모리에 다음 상태를 120초 보관한다.

- 플레이어 조건, 참여 상태, Down 횟수와 최초 절대 서버 출혈 기한
- 획득·소비·운반 중인 스크롤 원장과 납품 가치
- 손 1칸과 가방 4칸의 전체 인벤토리 및 리비전

같은 온라인 고유 ID가 제한 시간 안에 돌아오면 새 PlayerState와 Pawn에 복원한다. 연결이 끊긴 시간도 출혈 시간에 포함되며, 반복 재접속해도 최초 절대 기한이 연장되지 않는다. 재접속 유예 또는 출혈 기한이 끝나거나 원정이 Resolution에 도달하면 `Missing`으로 확정한다. 신규 late join은 관전자로 보낸다.

이 기능은 같은 Listen Server 프로세스 안의 메모리 복원 경로다. 자동 재시도, 원정 중 로비 재검색, Steam 재접속 UI, raw IP 사용자의 안정적인 동일 ID 보장, 호스트 재시작 후 복구는 없다. 따라서 재접속은 **서버 복원 기반만 있음**이며 end-to-end 기능으로 완료됐다고 보지 않는다.

## 7. 8방 던전

서버는 하나의 시드에서 다음 여덟 역할을 각각 한 번씩 생성한다.

1. Entry Records
2. Standard Stacks
3. Office
4. Flooded Archive
5. Bindery
6. Incinerator
7. Echo Hall
8. Sealed Storage

토폴로지는 입구에서 Sealed Storage까지 6방 주 경로와 1방짜리 가지 2개로 이루어진 연결 트리다. 목표 방은 입구에서 최소 4간선 떨어져 있다. 문 socket, 아이템·위협·계약 목표 marker, 시드와 checksum을 포함한 레이아웃 전체가 서버에서 생성되어 복제된다.

`TechSpike`는 이 레이아웃으로 8개 바닥, 방 표식, 연결 복도를 실제로 스폰한다. 같은 시드는 같은 레이아웃과 checksum을 만들며, 중복 역할·좌표, 단절, 순환, 잘못된 목표와 marker를 검증한다.

현재 marker는 생성 데이터일 뿐 실제 스폰 시스템이 소비하지 않는다. 스크롤·일반 아이템·위협·탈출 지점은 여전히 원점 주변 고정 좌표에 생성된다. 방별 벽·문·장애물·조명·환경 규칙·전리품 표·위협 표·목표 상호작용도 없다. 따라서 **레이아웃 생성과 회색 상자 표시는 구현됨**, **방별 플레이 구성은 기반만 있음**이다.

## 8. 서버 권위, 멱등성과 검증 게이트

### 공통 원칙

- 클라이언트는 줍기, 사용, 교환, 버리기, 준비, 채팅, 투표, 탈출의 의도만 전송한다.
- 게임 규칙, 아이템 결과, 조건 변화, 계약 보상, 저장·정산은 Listen Server가 확정한다.
- 권위 요청에는 가능한 한 요청 ID와 예상 리비전을 포함한다.
- 상호작용·인벤토리·파티처럼 멱등 원장을 쓰는 경로의 exact replay는 이전 결과를 돌려주고, 같은 ID의 다른 payload는 충돌로 거부한다. 스크롤은 정확한 인스턴스의 1회 소비로 중복 효과를 막는다.
- 월드 claim, 인벤토리, 장비, 파티, 제작, 캠페인 정산은 각각 독립적인 중복 방지 경계를 가진다.
- 저장 데이터는 경로가 아니라 Stable ID와 인스턴스 ID의 의미를 보존해야 한다.

### 현재 테스트 근거

자동화 테스트는 인벤토리 스택·라우팅·리비전, claim token과 rollback, 상호작용 replay, 6계열 resolver와 요청 ID 독립 오작동, 장비 위조·내구도, 파티 준비·투표·채팅·강퇴 원장 정리, 계약 중복 증거, 제작 원자성, 캠페인 3슬롯·저장 rollback, 런 상태·절대 출혈 기한·소음, OSS 세션 등록명, 위협 예산·감지, 던전 결정성·토폴로지를 다룬다.

가장 최근 전체 보고서 `Saved/AutomationReports/VerticalSlice-20260727-AuthorityVerified`는 총 65개 중 64개 clean success, 의도한 잘못된 런 단계 거부 경고를 포함한 success 1개, 실패·미실행 0개다. 같은 최종 코드로 Win64 Development Editor와 Game 빌드, `TechSpike` cook·stage·pak·IoStore·archive를 통과했다. 창 모드 `-nosteam` 패키지 2·4프로세스 smoke도 모든 프로세스가 상태 0으로 종료했고, 각각 2·4인 탈출과 호스트 캠페인 정산 1회를 확인했다. 이 검증은 실제 Steam 계정 간 로비·초대·음성을 대체하지 않는다.

2026-07-27의 수동 2인 Listen Server PIE에서는 양방향 이동, 질주 스태미나, 월드 아이템 제거 복제, 손 1칸·가방 4칸 HUD, 숫자 키 교환, 버리기·재획득, 스크롤 1회 소비와 양쪽 제거를 확인했다. 동시에 다음 표현·흐름 결함도 확인했다.

- `FirstPersonHands` 컴포넌트에는 skeletal mesh가 없어 실제 1인칭 손이 보이지 않는다.
- 버린 스크롤은 범용 `ASPWorldItem`으로 다시 생성되고 정의의 픽업 메시를 해석하지 않아 큐브로 표시된다.
- 파티가 준비되지 않아 런이 `Preparing`인 상태에서도 획득·사용·탈출이 허용된다. 이 상태에서 전원이 탈출하면 추출 수는 2/2가 되지만 Preparing 가드 때문에 Resolution과 정산이 시작되지 않는다.

## 9. 남은 백로그와 권장 구현 순서

### P0 — 현재 수직 슬라이스를 신뢰할 수 있게 만들기

1. 1인칭 손·원격 바디의 최종 컴포넌트 구조와 교체 가능한 아트 계약을 확정한다.
2. 픽업 외 스크롤 사용·인벤토리 교환·버리기·탈출·투표에 서버 결과 UI를 붙인다.
3. 거리, LOS, 소유권, stale revision, 같은 아이템 동시 claim, 요청 재전송을 2프로세스 적대적 테스트로 자동화한다.
4. 통과한 패키지 2·4프로세스 smoke를 반복 스크립트와 CI 게이트로 고정하고 packet loss·cross-machine soak를 추가한다.
5. G1/G2 성공 기준을 수치화하고 Echo Hunter가 실제 발소리에 반응하는 전체 루프를 플레이테스트한다.

### P1 — 시스템을 실제 게임 선택으로 연결하기

1. 던전 marker가 아이템·위협·계약 목표·탈출 지점을 배치하도록 바꾸고 8방을 실제 탐험 동선으로 만든다.
2. 나머지 5개 스크롤 Data Asset과 각인, 픽업, VFX/SFX/UI를 제작하고 6계열 네트워크 적용을 검증한다.
3. 장비 상태를 플레이어 컴포넌트·인벤토리·저장·재접속·Paper Eater·제작 UI에 연결한다.
4. 계약 게시판, 정산함→보관함 이동, 제작 작업대와 중요 제작 투표를 허브 흐름으로 연결한다.
5. 위협 NavMesh, 문 통과, 막힘 복구, 예고·피격·후퇴 연출과 디렉터 공포 이벤트 표현을 추가한다.
6. Steam 로비·친구 초대·오류·음성 UI와 패키지 계정 간 검증을 마친다.
7. 120초 재접속을 Steam과 raw IP 양쪽에서 end-to-end로 검증하고 재접속 발견 경로를 설계한다.

### P2 — 콘텐츠 확장 전에 결정할 기획 항목

- 대형 화물 획득 시 손 아이템을 자동으로 바꿀지, 명시적으로 비우게 할지
- 장비가 인벤토리 칸을 계속 점유하는지와 파손 장비의 필드·허브 처리
- 정산함 아이템을 자동 보관할지 플레이어가 선택할지
- 계약 보상을 호스트 캠페인 전체에 줄지 개인 기여도와 분리할지
- 계약 실패 패널티, 길드 랭크 해금, 경제 sink와 제작 결과의 소유권
- 원정 중 강퇴 시 운반 아이템을 월드에 떨어뜨릴지 소멸시킬지와 보상·패널티 정책
- 붕괴 중 탈출 규칙과 연결 끊긴 플레이어에게 120초보다 run deadline을 우선할지
- Revelation이 보여 줄 정보 범위와 Paper Eater가 운반 중 아이템도 공격할지
- 공포 이벤트의 반복 방지, 플레이어별 노출과 접근성 옵션
