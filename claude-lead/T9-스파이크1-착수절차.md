# T9. 스파이크 1 착수 절차서

2026-10-07 · 설계 v2.2 동기화 · 설계 개정 2026-10-06 · D8 유지 · Codex · 사용자가 순서대로 실행할 작업 지침

**구현을 시작하는 날에는 §1을 따라 개발 도구 설치 → 새 C++ 프로젝트의 첫 빌드 → Git·LFS 확인 → 첫 로컬 커밋까지 진행한다.** 그다음 §2의 파일 목록을 보면서 §3의 하루 작업 카드를 하나씩 수행한다. 기능을 만들기만 한 상태와 다른 PC에서 검증한 상태를 구분한다. 설치·빌드 전에 실제 배포 중인 목표 엔진 버전과 API를 공식 자료로 재확인한다. 이번 동기화는 문서 작업이며 설치·프로젝트 생성·게임 프로젝트의 Git 초기화·첫 커밋을 실행하지 않는다.

이 문서에 적힌 설치·명령·파일 생성은 **사용자가 앞으로 실행할 절차**다. 초안 작성과 이번 동기화에서 엔진 설치·프로젝트 생성·코드 작성·게임 프로젝트의 Git 초기화·첫 커밋·빌드를 실행하지 않았다. 명령 예시는 도구 조작용이며 C++ 구현 코드는 포함하지 않는다.

## 1. 0일차 준비 — 이 순서대로 실행

### 1.1 경로와 도구를 준비한다

**[추천] 경로 예시:** 프로젝트는 `C:\Users\Home\Dev\ScrollPeddler`, 패키지는 `C:\Users\Home\Dev\Builds\ScrollPeddler`, 원본 로그·영상은 `C:\Users\Home\Dev\TestEvidence\ScrollPeddler`에 둔다. 짧은 영문 경로를 사용하고 현재 기획 문서 폴더와 새 Git 저장소를 분리한다. 아래 경로가 이미 사용 중이면 덮어쓰지 말고 비어 있는 별도 경로를 정한다. 이 경로들은 아직 생성하지 않았다.

| 순서 | 직접 할 일 | 확인하고 다음으로 넘어갈 조건 |
|---:|---|---|
| 0-01 | 프로젝트·패키지·증거 위치를 정하고 디스크 여유를 확인한다. 실제 설치 화면의 예상 용량 외에 빌드와 패키지를 둘 여유도 남긴다 | 서로 다른 폴더이며 기존 자료를 덮어쓰지 않음 |
| 0-02 | Epic Games Launcher → Unreal Engine → Library에서 **5.8 정식 버전**을 설치한다. Options에서 Windows 작업에 필요한 구성과 Templates and Feature Packs를 확인한다 | Launcher의 5.8 타일로 에디터 실행 가능. 설치한 정확한 5.8.x 버전을 기록 |

PowerShell에서 **확인만** 하는 명령:

```powershell
git --version
git lfs version
```

Git은 되는데 LFS만 실패하면 [Git LFS 공식 배포](https://git-lfs.com/)를 설치한 뒤 새 PowerShell에서 다시 확인한다. 이때 프로젝트를 먼저 커밋하지 않는다.

**[사실]** Launcher는 엔진 버전과 설치 구성요소를 선택하는 설치 경로를 제공한다. [Epic 엔진 설치](https://dev.epicgames.com/documentation/unreal-engine/install-unreal-engine)

### 1.4 폴더와 Git 제외 규칙을 만든다

아래는 **향후 프로젝트 루트 `C:\Users\Home\Dev\ScrollPeddler` 안의 경로**다. 처음부터 빈 하위 폴더를 모두 만들 필요는 없다. 파일을 처음 만드는 날 해당 폴더를 만든다. 에셋의 이동·이름 변경은 Content Browser에서 한다.

| 경로 | 넣을 것 | 생성 시점 |
|---|---|---|
| `Source/ScrollPeddler` | 실행 모듈 하나와 생성된 템플릿 코드 | 자동 생성 |

| `/.idea/` | 다른 IDE 사용 시 로컬 작업 자료 |

| `*.suo` | 개인 IDE 상태 |

| `/Builds/` | 실수로 프로젝트 안에 만든 패키지 |

**[추천]** `Content`, `Config`, `Source`, `.uproject`, `.gitattributes`, `DataSource`, `Docs`는 추적한다. **`Build/`와 `Builds/`는 다르다.** 원본 빌드 설정·자원이 들어갈 수 있는 `Build/`를 일괄 제외하지 않는다. 플러그인을 추가할 때는 배포에 필요한 바이너리가 있는지 확인한 뒤 플러그인별 제외 규칙을 정한다.

**[사실]** `.gitignore`는 이미 추적 중인 파일을 자동으로 추적 해제하지 않는다. 따라서 첫 추가·커밋 전에 제외 규칙을 마련한다. [Git gitignore](https://git-scm.com/docs/gitignore)

### 1.5 Git·LFS를 설정하고 첫 커밋한다

다음 명령은 **새 프로젝트 폴더에서만** 실행한다. PowerShell에 한 줄씩 입력하고 결과를 확인한다. 현재 기획 문서 저장소에서 실행하지 않는다.

```powershell
Set-Location -LiteralPath 'C:\Users\Home\Dev\ScrollPeddler'
Get-Location
git rev-parse --show-toplevel
```

마지막 명령이 ‘저장소 아님’으로 끝나는 것은 새 폴더에서 정상이다. 이미 다른 최상위 저장소 경로가 나오면 중첩 저장소를 만들지 말고 경로부터 바로잡는다. 그다음 아래를 실행한다.

```powershell
git init --initial-branch=namul/spike1
git lfs install --local
git lfs track "*.uasset"
git lfs track "*.umap"
git config --get user.name
git config --get user.email
```

이름·이메일이 없거나 다른 사람 것이면 이 저장소에서만 `git config user.name "본인의 이름"`, `git config user.email "본인의 Git 이메일"`로 바꾼다. 예시 문구를 그대로 본인 정보로 저장하지 않는다. 원본 PSD·FBX·WAV 등 큰 파일을 나중에 보관할 경우 **처음 추가하기 전에** 필요한 확장자만 LFS 규칙에 더한다.

**[사실]** `git init --initial-branch`는 첫 브랜치 이름을 지정한다. LFS `--local`은 저장소 설정을 사용하고, `track`의 결과인 `.gitattributes`도 커밋해야 한다. [Git init](https://git-scm.com/docs/git-init), [Git LFS install](https://github.com/git-lfs/git-lfs/blob/main/docs/man/git-lfs-install.adoc), [Git LFS 시작 안내](https://git-lfs.com/)

이제 제외·LFS 규칙을 검사한 뒤 첫 커밋에 넣을 파일만 추가한다.

```powershell
git check-ignore -v 'Saved/Logs/probe.log' 'Intermediate/probe.txt'
git check-attr filter -- 'Content/ScrollPeddler/Maps/L_Spike01.umap'
git add -- .gitignore .gitattributes ScrollPeddler.uproject Config Content Source
git status --short
git diff --cached --stat
git lfs ls-files
```

| 출력 | 기대하는 내용 |
|---|---|
| `check-ignore` | Saved·Intermediate가 어느 규칙으로 제외됐는지 나옴. 검사 경로의 probe 파일을 만들 필요는 없음 |
| `check-attr` | 시험 맵의 filter 값이 `lfs` |
| `status`·`diff` | 원본 코드·설정·콘텐츠와 두 Git 규칙 파일. Binaries·Saved·Intermediate·패키지가 없어야 함 |
| `lfs ls-files` | 추가한 `.uasset`·`.umap` 목록이 보임. `.gitattributes`만 있고 에셋 목록이 비면 추가 상태·필터 확인 |

`Docs/Checks`에 직접 만든 환경 메모가 있으면 그 파일도 별도로 추가한다. 생성된 `Build/`에 원본 설정·아이콘 등이 있다면 내용을 확인해 그 원본도 추가한다. 빠진 파일이 있는지는 `git status`로 확인한다. **목록을 검토한 뒤 사용자가 직접** 다음을 실행한다. AI에게 실행을 맡기면 기존 작업 규칙에 따라 이 목록과 커밋 문구를 보여 주고 커밋 승인을 받은 뒤 실행하게 한다.

```powershell
git commit -m "[Chore] UE 5.8 1인칭 C++ 프로젝트와 Git LFS 초기 설정"
git status --short
git log -1 --oneline
```

**[추천]** 첫 커밋은 로컬 기준점이다. 원격 저장소를 만들거나 푸시하는 절차는 별도 요청 때 진행한다. 로컬 커밋만으로 다른 디스크에 백업됐다고 기록하지 않는다. 이미 일반 Git으로 큰 파일을 커밋했다면 이력을 자동 재작성하지 말고 상태와 가능한 복구 방법을 먼저 검토한다.

## 4. 검증 체크리스트와 2인 접속 방법

### 4.1 D1 — 에디터에서 빠르게 두 명을 확인한다

**[사실]** PIE는 에디터에서 실행하는 시험 기능이다. `Play as Listen Server`의 플레이어 수에는 호스트가 포함된다. 한 프로세스에 여러 플레이어를 실행하면 빠르지만 실제 여러 PC 조건과는 다르다. [Epic PIE 멀티 옵션](https://dev.epicgames.com/documentation/unreal-engine/play-in-editor-multiplayer-options-in-unreal-engine)

| 순서 | 조작 |
|---:|---|
| 1 | L_Spike01을 연다. 바닥 위에 서로 떨어진 Player Start를 둔다. 맵의 GameMode Override가 의도한 BP_SpikeGameMode인지 확인한다 |
| 2 | Play 옆 메뉴 또는 Editor Preferences → Level Editor → Play → Multiplayer Options를 연다 |
| 3 | Number of Players = **2**, Play Net Mode = **Play as Listen Server**, Launch Separate Server = **끔** |
| 4 | 빠른 확인은 Run Under One Process = **켬**, 실행은 **New Editor Window (PIE)**. 다른 UI에서는 Use Single Process라는 이름일 수 있음 |
| 5 | Play를 누르고 각 창을 번갈아 클릭해 이동·시점을 바꾼다. 어느 창이 호스트인지 역할 표시/로그로 확인한다 |
| 6 | 종료 후 Run Under One Process를 **끔**으로 바꿔 별도 프로세스도 확인한다. 계속 실패하면 아래 패키지 경로로 증상을 구분한다 |

- [ ] 두 창이 같은 방에 접속했고 양쪽에서 상대 몸을 볼 수 있다.
- [ ] 첫 번째 창을 움직이면 첫 번째 캐릭터만, 두 번째 창을 움직이면 두 번째 캐릭터만 움직인다.
- [ ] 원격 창이 호스트 카메라를 조작하지 않는다.
- [ ] 종료·재실행 뒤에도 재현된다. PIE 자동 연결을 Steam 세션·초대 성공으로 기록하지 않는다.

### 4.2 D2 — Windows Development 패키지를 만든다

**[사실]** 패키지의 시작 맵은 Game Default Map으로 지정하며, Development 설정과 Windows Package Project 경로로 시험용 패키지를 만들 수 있다. [Epic 패키징](https://dev.epicgames.com/documentation/unreal-engine/packaging-your-project)

| 순서 | 직접 할 일 | 완료 증거 |
|---:|---|---|
| 1 | Save All. Project Settings → Maps & Modes에서 Game Default Map = L_Spike01 확인 | Editor Startup Map만 바꾸고 끝내지 않았음 |
| 2 | Project Settings → Packaging 검색. Build Configuration = **Development**, List of maps to include in a packaged build에 `/Game/ScrollPeddler/Maps/L_Spike01` 추가 | 실제 저장 경로와 일치. 시험에 필요한 표·소품도 참조로 포함 |
| 3 | Platforms → Windows → Use Project Setting **(Development)** 확인 → Package Project | 출력 위치는 프로젝트 밖의 `C:\Users\Home\Dev\Builds\ScrollPeddler` |
| 4 | Output Log에서 완료 확인. 실패면 마지막 Unknown Error보다 앞에 있는 첫 컴파일·Cook·SDK 오류를 기록 | 빌드 성공과 패키징 성공을 구분 |
| 5 | 출력 폴더의 게임 `.exe`를 단독 실행해 기본 조작 확인 | 에디터 없이 시험 맵·캐릭터가 열림 |
| 6 | 정확한 `.exe` 전체 경로·패키지 빌드 ID·기반 커밋 ID를 적고 실행한 게임을 종료 | 다음 호스트 실행 때 포트/창이 중복되지 않음 |

**[추천]** 아래 명령의 `.exe` 위치는 흔한 출력 형태의 예시다. 파일 탐색기에서 **실제로 생성된 게임 실행 파일** 경로를 복사해 넣는다. 다른 PC에는 `.exe`만이 아니라 **Windows 패키지 전체 폴더**를 복사한다. 별도 Server/Client 빌드 Target이나 `-server` 옵션은 이번 리슨 서버 시험에 추가하지 않는다.

### 4.3 같은 PC에서 게임 두 프로세스를 실행한다

아래는 **[추천] Development 패키지용 실행 절차**다. 문서 작성 중 UE 5.8 패키지에서 실행한 명령은 아니다. 맵 URL은 이 문서의 L_Spike01 경로를 사용한다.

**PowerShell 창 1 — 호스트부터 실행:**

```powershell
$spikeExe = 'C:\Users\Home\Dev\Builds\ScrollPeddler\Windows\ScrollPeddler.exe'
& $spikeExe '/Game/ScrollPeddler/Maps/L_Spike01?listen' '-port=7777' '-log' '-Log=SpikeHost.log' '-windowed' '-ResX=960' '-ResY=540'
```

호스트의 시험 맵이 열리면 **PowerShell 창 2 — 참가자 실행:**

```powershell
$spikeExe = 'C:\Users\Home\Dev\Builds\ScrollPeddler\Windows\ScrollPeddler.exe'
& $spikeExe '127.0.0.1:7777' '-log' '-Log=SpikeClient01.log' '-windowed' '-ResX=960' '-ResY=540'
```

| 확인 | 성공 증거 |
|---|---|
| 호스트 | 플레이 가능한 창이며 리슨 서버 역할. 전용 서버처럼 화면 없는 실행이 아님 |
| 참가자 | 호스트가 있는 같은 방에 합류. 각 화면에 연결된 두 캐릭터가 존재 |
| 이동 | 창을 번갈아 클릭해서 이동한 결과가 다른 화면에도 나타남 |
| 기록 | 호스트·클라이언트 로그를 서로 다른 파일로 구분. 실행 로그에서 실제 저장 위치를 확인해 증거 폴더에 복사 |
| 한계 | 같은 PC 창 두 개는 프로세스 분리 검사. 한 사람이 번갈아 조작한 것을 두 사람의 협동 재미 회차로 세지 않음 |

검사가 끝나면 **두 게임 프로세스를 모두 정상 종료한 뒤** 로그를 증거 폴더에 보관한다. 다음 LAN 시험에서 같은 포트의 호스트를 새로 띄우기 전에 이전 호스트가 남아 있지 않은지 확인한다.

**[사실]** UE 명령줄은 맵/접속 URL과 실행 옵션을 받을 수 있고 기본 서버 포트는 7777이다. 창 크기·로그 옵션도 공식 레퍼런스에 있다. [Epic 명령줄](https://dev.epicgames.com/documentation/unreal-engine/command-line-arguments-in-unreal-engine), [Epic 실행 인자](https://dev.epicgames.com/documentation/unreal-engine/unreal-engine-command-line-arguments-reference)

**[사실·문서 버전 한계]** `?listen`의 뜻을 직접 설명하는 URL 옵션 표는 [Epic 4.27 명령줄 문서](https://dev.epicgames.com/documentation/unreal-engine/command-line-arguments?application_version=4.27)에서 확인했다. 위 5.8 실행 절차의 실제 성공 여부는 이 단계에서 로그와 화면으로 검증한다. 단순히 창이 두 개 열렸다고 리슨 서버 성공으로 처리하지 않는다.

| 1 | 이전 시험의 모든 게임을 정상 종료한 상태에서, 두 PC를 같은 신뢰하는 LAN에 연결하고 동일한 패키지 전체 폴더를 준비한다 |
| 2 | 호스트 PC에서 §4.3의 호스트 명령으로 실행한다 |
| 3 | 호스트 PowerShell에서 `ipconfig` 실행 → 현재 연결된 Ethernet/Wi-Fi의 **IPv4 주소**를 적는다. VPN·가상 어댑터 주소와 구분 |
| 4 | 클라이언트 PC의 아래 `$spikeExe`를 그 PC의 실제 경로로 바꾸고, 주소를 위에서 읽은 **호스트 IPv4**로 바꿔 실행한다 |
| 5 | 각자 키보드로 동시에 이동한다. 양쪽 게임을 종료하고 로그를 보관한 뒤 역할을 바꾼다. 새 호스트의 IPv4를 다시 읽어 참가 주소도 바꾸고 한 번 더 확인한다 |
| 6 | 양쪽 게임 종료 후 두 로그·빌드 ID·역할·주소·성공/실패를 같은 시험 기록에 연결한다 |

```powershell
$spikeExe = 'C:\Users\Home\Dev\Builds\ScrollPeddler\Windows\ScrollPeddler.exe'
& $spikeExe '192.168.0.10:7777' '-log' '-Log=SpikeClientLAN.log' '-windowed' '-ResX=960' '-ResY=540'
```

`192.168.0.10`은 예시이므로 그대로 복사하지 말고 실제 호스트 주소로 바꾼다. 다른 PC에서 `127.0.0.1`을 쓰면 자기 PC를 찾는다. 연결이 막히면 Windows 보안 → 방화벽 및 네트워크 보호 → 방화벽에서 앱 허용에서 **실제로 실행된 게임 앱**의 개인 네트워크 허용을 확인한다. 방화벽 전체를 끄는 절차는 쓰지 않는다.

**[사실]** `ipconfig`는 네트워크 어댑터의 IPv4 등 설정을 보여 준다. Windows는 앱별 방화벽 허용을 제공한다. Epic의 네트워크 시험 옵션은 게임 서버 포트를 UDP로 설명한다. [Microsoft ipconfig](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/ipconfig), [Microsoft 앱 허용](https://support.microsoft.com/en-us/windows/security/firewall/risks-of-allowing-apps-through-windows-firewall), [Epic 서버 포트](https://dev.epicgames.com/documentation/unreal-engine/play-in-editor-multiplayer-options-in-unreal-engine)

- [ ] 두 PC의 빌드·콘텐츠 개정이 같다.
- [ ] 서로 다른 PC에서 동시에 움직이고 양쪽 결과가 보인다.
- [ ] 역할을 바꿔도 성공한다.
- [ ] 호스트 종료는 시험 중단으로 기록한다. 자동 호스트 이전·저장 복구를 구현했다고 적지 않는다.
- [ ] 원격 인터넷 직접 접속·공유기 개방·Steam 초대는 이번 LAN 성공과 구분한다. 같은 PC 통과만으로 1단계를 최종 통과시키지 않는다.

D15의 **4인 시험은 호스트 1명 + 참가자 3명**이다. 호스트를 하나만 실행하고 세 참가자가 같은 호스트 IPv4·7777로 접속한다. 각 참가자의 로그 이름을 `SpikeClient01.log`·`02`·`03`으로 구분하고, 맵의 시작 위치도 네 명분인지 확인한다. 정식 4인 재미 회차는 네 사람이 각자 조작한다.

### 4.6 D16 — 지연·손실을 설정하고 반드시 해제한다

**[사실]** UE의 `NetEmulation`은 송신·수신 지연과 손실을 설정하고 `NetEmulation.Off`로 끌 수 있다. [Epic 네트워크 에뮬레이션](https://dev.epicgames.com/documentation/unreal-engine/using-network-emulation-in-unreal-engine)

먼저 정상 연결을 만든다. **원격 클라이언트 한 창의 게임 콘솔**에 입력한다. PowerShell이 아니다. 콘솔이 열리지 않으면 Project Settings → Input → Console Keys를 확인하고 Development 패키지를 다시 만든다. 아래 숫자는 **[추정] 재현용 시작 조건**이며 출시 품질의 합격선이 아니다.

| 순서·조건 | 클라이언트 게임 콘솔에 한 줄씩 입력 | 뜻 |
|---|---|---|
| N0 정상 | `NetEmulation.Off` | 이 프로세스에서 넣은 조건 초기화 |
| N1 상행 지연 | 먼저 Off → `NetEmulation.PktLagMin 100` → `NetEmulation.PktLagMax 100` | 클라이언트→서버에 지연 100ms 추가 |
| N2 하행 지연 | 먼저 Off → `NetEmulation.PktIncomingLagMin 100` → `NetEmulation.PktIncomingLagMax 100` | 서버→클라이언트에 지연 100ms 추가 |
| N3 손실만 | 먼저 Off → `NetEmulation.PktLoss 5` | 클라이언트 송신에 5% 손실 |
| N4 양방향 혼합 | 먼저 Off → 송신 LagMin/Max 각각 50, 수신 IncomingLagMin/Max 각각 50 → PktLoss 1, PktIncomingLoss 1 | 추가 왕복 지연 약 100ms 조건에 양방향 각 1% 손실. 실제 왕복시간 별도 기록 |
| N5 변동 지연 | 먼저 Off → 송신 LagMin 50 / LagMax 100 | 매 요청의 도착 간격이 달라질 때의 판정 확인 |
| 종료 | 조건을 넣은 **모든 프로세스**에서 `NetEmulation.Off` | PIE의 Enable Network Emulation도 켰다면 별도로 끔 |

N4의 입력을 펼치면 다음과 같다.

```text
NetEmulation.Off
NetEmulation.PktLagMin 50
NetEmulation.PktLagMax 50
NetEmulation.PktIncomingLagMin 50
NetEmulation.PktIncomingLagMax 50
NetEmulation.PktLoss 1
NetEmulation.PktIncomingLoss 1
```

각 조건에서 §4.5의 단일 소비·지연 대상·접착 해제·상태 만료를 반복한다. 호스트와 클라이언트 모두에 같은 조건을 무작정 넣지 않는다. `PktLag 100` 같은 다른 지연 명령이나 PIE의 에뮬레이션을 함께 켜 중복 지연을 만들지 않는다. 개발 재현 도구의 같은 요청 ID 반복은 패킷 손실과 다른 시험이므로 따로 기록한다.

| 조건 ID | 실행한 프로세스·설정값 | 실제 왕복시간 | 승인/중복/거부 수 | 소비/발동 수 | 최종 수량·효과 종료 일치 | 최대 이동 보정·수렴 시간 | 오류 사건 ID |
|---|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |  |

검사 후 정상망에서 한 번 더 사용·손 해제한다. 기술 기준은 **중복 소비·음수 수량·종료 뒤 영구 이동 잠금이 없고, 통신 회복 뒤 서버의 최종 상태로 수렴하는 것**이다. 보정 거리·수렴 시간의 체감 합격값은 측정 기록을 보고 정한다.

## 5. 첫 회차 실험 진행표

### 5.1 회차 시작 전에 준비한다

입력 기준은 현행 개발 계획의 **2인 두 팀·4인 두 팀부터**, 각 정식 회차 **10분 안 독립적인 예상 밖 웃긴 사건 3회 이상 + 사건별 원인 설명**이다. 작은 표본의 통과가 전체 게임의 재미 검증을 대신하지 않는다.

- [ ] D15~D17의 중복 소비·상태 불일치·이동 잠금 결함을 해결했다.
- [ ] 전원 같은 패키지·콘텐츠 개정이며, 인위 지연 설정을 해제했다.
- [ ] 회차 ID, 인원, 호스트, 참가자 익명 ID, 빌드 ID, 조작 안내 완료를 기록했다.
- [ ] 7룬·12문장 목록이며, 24초 강제 상태·시험 지급 메뉴는 일반 참가자 화면에서 빠져 있다.
- [ ] 목표는 **꾸러미를 도착 보관대까지 운반**으로 통일했다. 사고를 내거나 특정 조합을 쓰라고 지시하지 않는다.
- [ ] 물·이끼·먹물·분말·송풍기·등기구·고정 탄성 매트 상태와 시작 꾸러미를 같은 기준으로 초기화했다.
- [ ] 관찰자는 실험 중 해결법을 유도하지 않는다. 기술 문제와 실제 소동을 별도 표시한다.

### 6.2 복제·소비·타이머·중첩

**[사실]** Server RPC는 소유 연결과 복제 설정에 영향을 받고, 다른 Actor 간 RPC·개별 복제 알림의 도착 순서를 일반적으로 하나의 순서로 가정할 수 없다. | 호스트만 조작/사용 가능 | 입력의 로컬 소유자와 게임 결과의 서버 권한을 구분. `HasAuthority` 조건 안에 로컬 입력을 가두지 않았는지 확인 | 원격 창에서 D1 이동, D15 전 기능 |

| 호스트 효과음만 두 번 남 | 서버 변경과 로컬 표시에서 같은 사건을 재생하는지 확인. `EventId + 표현 ID`로 중복 차단 | 호스트/원격 각 1회 |

예시 요청문:
