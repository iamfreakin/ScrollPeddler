## 1. 데이터 구조

### 1.1 정의 에셋과 표

**[사실]** `UDataAsset`은 시스템 정의 데이터를 담으며, `UPrimaryDataAsset`은 Primary Asset ID와 Asset Manager의 로드 관리를 지원한다. `UDataTable`은 `FTableRowBase` 기반 행 구조에 CSV를 가져올 수 있다. [Epic Data Assets](https://dev.epicgames.com/documentation/en-us/unreal-engine/data-assets-in-unreal-engine), [Epic Data Driven Gameplay](https://dev.epicgames.com/documentation/en-us/unreal-engine/data-driven-gameplay-elements-in-unreal-engine)

| 자료 | 권장 형태 | 핵심 열·참조 |
|---|---|---|
| 전체 정의 묶음 | `UScrollDefinitionCatalog : UPrimaryDataAsset` 1개 | 아래 표, 표시용 에셋 묶음, `ContentRevision`. 시작할 때 룬 정의를 읽어 사용 중 디스크 로드를 피함 |
| 동사 7개 | `DT_RuneVerbs` / `FScrollVerbRow` | `RuneId`, 표시명 키, `ExecutorId`, 원료 ID, 기본 지속·세기·표현 ID. 빛나라·붙어라·당겨라·튕겨라·달궈라·가려라·걸러라 |
| 대상 6개 | `DT_RuneTargets` / `FScrollTargetRow` | `RuneId`, 선택 방식, 허용 대상 종류, 기본·넓게 범위, 표면 선택 방식. 물건·바닥·벽·나·너·주변 |
| 수식 5개 | `DT_RuneModifiers` / `FScrollModifierRow` | `RuneId`, 준비시간·지속·세기·사거리·동사 먹 비용 조정, 반동·소음 표현 참조. 잠깐·오래·넓게·세게·멀리 |
| 기본 결과42개 | `DT_BasicResults` / `FScrollBasicResultRow` [추천] | `VerbId + TargetId`의7×6 키, 수신 종류·몸/부착물/표면·접촉 필요·고정체 무효 이유·표현 참조. 본편42개 누락/중복 검사, 효과 클래스42개를 만들지 않음 |
| 실험 사용 목록 | `UScrollExperimentDefinition` | 해당 회차가 허용하는 룬 ID 집합. 전체 정의와 분리해 1차의 7룬·12문장만 노출 |
| 반응 정의 | `DT_Reactions` | `ReactionId`, 필요한 상태·성질, 처리 단계, 승인된 계수 참조, 결과 이유 ID. 실행기는 C++에 등록된 것만 선택 |
| 재료 정의 | `DT_Materials` | `MaterialId`, 표시명·단위, 물 취약성, 원료·가공 관계, 성질 ID, 표현 에셋 참조 |

표는 수치와 연결을 바꾸는 수단이다. 새 물리 행동을 텍스트 한 칸으로 실행하는 범용 스크립트 엔진은 만들지 않는다. 210문장은 **7 × 6 × 5의 조합**이며 210개 효과 클래스나 고정 제조법 행을 만들지 않는다. 본편에서는 통합본의 기본 결과42개를 빠짐없이 확인하고 수식 하나의 준비·지속·세기·범위·동사 먹 비용 계산을 적용한다. 42칸 설명과 수식 수치 표는 통합본에서 관리하며 이 기술 문서에 중복 복사하지 않는다. 오래+넓게처럼 수식 둘을 겹치는 문법은 없다.

| ID 원칙 | 구조 |
|---|---|
| 정의 ID | `FName` 기반의 안정 ID. 예: `Verb.Adhere`, `Target.Creature`, `Modifier.Brief`. 표시 이름을 바꾸거나 표 행 순서를 바꿔도 유지 |
| 번역·표시 | 표시명은 `FText`·String Table 키로 따로 둠. 한국어 이름·아이콘 파일 경로를 저장 ID로 쓰지 않음 |
| 개별 기록 ID | 도안·아이템 묶음·공방·원정은 `FGuid`. 참가자 세션 ID와 영구 계정 식별자는 별도 |
| 상태·이유 분류 | 중앙에 정의한 이름 또는 Gameplay Tag. 임의 문자열을 각 소품에서 새로 만들지 않음 |
| 버전 | `ContentRevision`은 정의 묶음, `PatternVersion`은 도안 편집, `StateRevision`은 실행 상태, `SaveSchemaVersion`은 저장 형식. 서로 대체하지 않음 |

### 1.2 문장·저장 도안·휴대 도안판

| 자료형 후보 | 필드 | 지켜야 할 조건 |

| `FScrollCraftAction` | 현장 한 장 제작의 `ActionId`, 도안 복사, 재료 예약, 완료 예정 시각 | 완료 전 취소는 제품·재료 소비 없음. 완료 승인 때 한 장 생성하며 `bSealed=false` |

**[추천]** 공동 도안 수정 요청은 사용자가 본 `ExpectedPatternVersion`을 보낸다. 서버 버전이 달라졌으면 덮어쓰지 않고 충돌 결과·현재 버전을 돌려준다. 편집 표시·복사본 제공 방식은 T2가 정한다. 배우지 않은 룬의 제작은 서버 지식 집합으로 검사하며, 완제품 보유와 룬 해금은 별개다.

| 스크롤 묶음 합치기 키 | 문장, 도안 버전, 봉인 여부, 제조 이력 등 필요한 출처 키 | 봉인·미봉인 또는 다른 제조 버전을 한 묶음으로 섞지 않음. 분할한 묶음은 새 ID와 원본 출처를 가짐 |
| `FMaterialStack` | `StackId`, `MaterialId`, 수량, `ContainerId`, 출처·원정 ID | 물 취약성은 정의에서 조회. 칸마다 습도·품질·건조 시간을 저장하지 않음 |
| `FInventoryContainer` | `ContainerId`, 종류, 소유 범위 ID, 아이템 목록·개정 번호 | 공방·가방·손·월드의 위치를 같은 자료로 표현. 하나의 물품은 한 컨테이너에만 존재 |
| `FInventoryReservation` | `ReservationId`, 작업 ID, 묶음별 예약 수량 | 총수량과 예약량 분리. 사용 가능 수량 = 총수량 − 예약량. 예약 시점과 소비 시점을 혼동하지 않음 |
| `FWorkshopWallet` | `WorkshopId`, `Balance:int64`, `LedgerRevision` | 자금은 최소 화폐 단위의 정수. 부동소수 오차 방지. 최소 단위·가격은 T4가 결정 |
| `FInventoryTransaction` | 거래 ID, 원인 사건 ID, 이동·생성·소비·현금 증감 항목, 완료 상태 | 구매·제작·사용·봉인·파손의 중복 적용 방지. 상품 사용의 기회비용은 현금 차감 항목이 아님 |
| `FExpeditionItemRecord` | `ExpeditionId`, 확보 물품 ID, 현재 컨테이너, 안전 반출 여부, 정산 처리 ID | 바닥에 내려놓아도 추적. 미채집 자원은 이 장부에 넣지 않음 |

원본 도안 참조와 문장 복사를 함께 두는 이유는 도안 삭제·편집 뒤에도 무엇으로 제조했는지 알기 위해서다. 실행 중인 시전은 승인 시 계산한 값을 고정한다. 기존 제품도 최신 밸런스 수치를 따르는 D4-08을 유지한다. 문장·도안 버전·봉인·출처는 보존하고 이미 승인한 시전은 승인 당시 계산값으로 마친다(§8.2).

| 물 취약성 입력 기준 / 표시 자료 | 기술 처리 |
|---|---|
| 현행 취약 원재료 3종 | 바탕 종이·말린 되감이풀·먹주머니에 취약 표시. 기본 먹과 나머지 원재료는 내구 표시 |
| 모든 미봉인 스크롤 | 제품의 물때 판정은 `bSealed`에서 계산. 공방 미포장품·현장 급조품 모두 취약, 봉인품 보존. 제작 장소·상품 이름·저장 도안 유무로 추정하지 않음 |
| 가공 중간재 | 당김 먹·차광 먹은 말린 되감이풀·먹주머니의 취약성을 이어 별도 가공 정의로 표현. 환산량은 T4의 현행 표를 따르며 새 환산 수치를 추가하지 않음 |
| 화면 공통 자료 | `WaterRiskPresentation` 조회 하나로 재료의 물 취약성·제품의 봉인 상태·이유 ID 제공. 아이콘·위치·색은 T2 소관 |
| 일반 젖음과 물때 종료 | 젖음 상태 추가가 가방 삭제를 호출하지 않음. 후속 물때 서비스가 원정 장부를 대상으로 한 번 정산 |
| 물때 정산 | 확보품은 손·가방·바닥·수레·꾸러미에서 물품 ID로 한 번 판정. 취약 원재료·가공 먹·미봉인품 파손, 내구 확보품 입구 공동 회수. 안전 반출 재고·미채집 자원 제외. 제품 파손 뒤 제조 원재료·공방 돈을 추가 차감하지 않음 |

물때 정산의 자료형은 본편 확장을 위한 설계다. 스파이크 1에서 물때 복귀·파손 기능을 구현하지 않는다.

### 2.1 사람·몬스터·소품·표면의 공통 입구

| `UScrollAttributeComponent` | **젖음·열·빛·먹물·끈적임·탄성·가루·바람** 8상태와 활성 효과 목록 보관. 사람·AI 없는 생물 시험체·소품에 공통 부착 |

**[추천]** 장식 메시 전체를 효과 대상으로 자동 변환하지 않는다. T3가 지정한 반응 소품·표면에만 수신기를 붙인다. 바닥·벽은 단순 구체 겹침만으로 반대편 벽까지 묻히지 않도록 연결 표면과 차폐를 검사한다. [추천·v2.2 적용] 몸 효과는 몸·옷 외곽에 표시하고 가방 속 모든 재고에 복사하지 않는다. 별도 반응 소품·장착물은 물건 대상 수신기로 구분한다. 접착·탄성·열 표면은 실제 접촉 작용을 연결하며, 표면의 빛·먹막·여과는 밟은 몸에 새 도장으로 복사하지 않는다.

### 2.2 수명·최강 중첩·지속 결과

| 기록 | 필드·규칙 |
|---|---|
| `FActiveScrollEffect` | `EffectId`, 원인 사건 ID, 시전자, 수신 위치, 속성/기능 채널, 원래 세기, 시작 시각, **원래 종료 시각**, 원천 ID, 제거 이유 |
| 같은 효과의 경쟁 | 같은 수신 위치·속성·작용 채널에서 살아 있는 효과 중 가장 강한 것을 선택. 다른 속성이나 떨어진 표면까지 서로 덮어쓰지 않음 |
| 약한 효과 | 가려져도 목록과 원래 종료 시각 유지. 강한 효과가 끝나면 아직 유효한 약한 효과만 남은 시간 동안 적용 |
| 같은 세기 | 서버의 생성 순서·효과 ID로 일관되게 대표 원인을 선택. 같은 세기를 더해 증폭하지 않음 |
| 환경 공급 | 원천 ID와 연결·접촉 상태를 기록. 영구 원천 여부를 명시하고 접촉 종료·소품 제거 때 원천을 해제 |
| 실제 상태량 | 소모된 물기·남은 열량·표면 가루량은 반응용 장부로 관리. 효과의 최대 세기와 물질·에너지 잔량을 혼동하지 않음 |
| 파생 표현 | 최종 밝기·차광·김·부유 가루는 원본 상태를 읽어 계산. 광원의 원래 밝기에 반복해서 배율을 곱하지 않음 |
| 이미 일어난 결과 | 물건 이동, 떨어진 위치, 옮겨진 가루는 효과가 끝나도 되감지 않음. 효과 종료는 더 이상 작용하지 않는다는 뜻 |

검증용 시간 예시: 강한 A가 서버 시각 8에 끝나고, 뒤에 건 약한 B가 시각 10에 끝나면 A 종료 뒤 B는 2만큼만 남는다. A가 끝났다고 B의 전체 지속을 다시 시작하지 않는다. 이 숫자는 구현 검사 예시이며 게임 수치 제안이 아니다.

**[추천]** 접착은 막 `EffectId`와 실제 결합 `BindingId`를 분리한다. 결합에는 두 수신 위치·접촉점·이동 제약을 기록한다. 손 해제나 충분한 가열로 풀 때 해당 결합과 원인이 된 막을 같은 상태 변경에서 제거한다. 지워진 막의 오래된 접촉 통지로 재접착하지 않게 한다. 다른 막 전체를 지우거나 임의의 접착 면역 시간을 추가하지 않는다.

### 2.3 S1~S6 처리 순서와 반복 방지

| 처리 단계 | 반응 | 입출력과 순서 |
|---:|---|---|
| 0 | 입력 확정 | 시전·환경 공급·새 접촉·타이머 갱신을 서버 큐에 등록. 먼저 해당 시각까지의 만료와 이전 지속 구간을 정리하고 이전 상태를 복사 |
| 1 | **S6 젖음 + 열** | 이번에 사용할 열량과 물기 잔량으로 반응. 소모량을 기록하고 김 발생량을 한 번 출력. **남은 열만** 다음 단계에 전달 |
| 2 | **S2 열 + 끈적임** | S6 이후 남은 열과 접착 조건으로 해제 여부 결정. 젖음이 있는 상태에서 원래 열량을 다시 읽어 쓰지 않음 |
| 3 | **S1 젖음 + 등심 성질** | 반응 뒤 남은 젖음과 등심 성질로 발광을 다시 계산. 등심 없는 젖은 생물은 자동 발광하지 않음 |
| 4 | **S3 먹물 + 빛** | 위에서 산출한 빛을 먹막 덮임으로 감광. 광원 원본은 유지해 먹막 제거 시 현재 젖음 조건에 맞는 밝기로 복원 |
| 5 | **S4 탄성 + 새 충돌** | 새 충돌 번호에 한 번만 반발 적용. 접착 중에는 자동 해제하지 않으며 해제 뒤 **새 충돌**부터 작동. 속도 상한·재충돌 간격은 설정 참조 |
| 6 | **S5 바람 + 가루** | 실제로 이동 가능한 가루량을 표면에서 빼고 부유 가루로 옮김. 동일 공급분·동일 시간 구간을 반복 생성하지 않음 |
| 7 | 결과 확정 | 상태량·결합·이동 명령을 한 변경 묶음으로 확정하고 사건 하위 기록 생성. 영향받은 다른 수신기는 후속 큐로 처리 |

단계 번호는 동일 대상에서 결과를 일관되게 만드는 기술 순서다. 관련 없는 S4·S5까지 매번 계산한다는 뜻은 아니다. 표에 없는 반응은 만들지 않으며 R7·R8은 스파이크 1에서 비활성이다. 여과의 포집은 부유 가루에만 적용하는 동사 실행 기능이며 김 제거·산소·해독으로 확장하지 않는다. 당김도 새 속성 반응 번호로 추가하지 않는다. 기본 먹은 가려라의 먹막으로 해석하지 않는다.

| 무한 반복·중복 원인 | 막는 구조 |
|---|---|
| 상태가 여전히 참이라는 이유로 김 재생성 | `SourceInputId`·이번 처리 구간·소모 전후 잔량 기록. 같은 공급 열을 다음 처리에서 다시 투입하지 않음 |
| 겹친 약한 효과까지 열 공급을 합산 | 동일 채널의 최강 공급률만 시간 구간에 적분. 세기 변경·만료 시점에서 구간을 나눔. 잔량 감소는 별도 원장에 한 번 반영 |
| 반응이 다시 자신을 호출 | 직접 재귀 호출 금지. `RootEventId + ReceiverKey + ReactionId + InputRevision` 처리 키로 같은 입력 재처리 차단 |
| 연쇄 전체를 막아 정상 반응도 누락 | 새 상태 개정이나 새 공급분이면 다음 큐에서 허용. 사건 번호만 같다는 이유로 이후 반응 전부를 차단하지 않음 |
| 충돌 통지가 여러 부위·양쪽에서 도착 | 두 수신기·접촉 회차를 정렬한 `ContactId`로 합침. S4 재충돌 간격과 속도 상한을 서버에서 검사 |
| 가루·김 수가 폭증 | 원료 소비 없는 새 생성 금지. 한 처리 묶음의 연쇄 깊이·작업량 기술 한도를 두고 초과는 오류로 기록. 조용히 성공 처리하지 않음 |
| 화면 복제가 서버 반응을 다시 호출 | 표시 갱신 경로는 읽기 전용. 서버 상태 쓰기 함수만 반응을 등록 |

열·물기 단위와 소모 계수, 접착 해제 기준, 반발 상한·간격, 당김/여과의 단위·상한 등 **미결 게임 값**은 이 문서에서 확정하지 않는다. 통합본의 남은 결정·검증 목록을 따른다. S6 물기 소모 → 남은 열로 S2/열 위험 판정과 같은 공급분 재소모 금지만 먼저 고정하며, 시험에 쓰는 개발자 설정값은 미검증 값·설정 개정으로 기록한다.

### 2.4 매 프레임 전체 검색을 피하는 실행

**[사실]** `FTimerManager`는 지연·반복 실행을 예약하고 핸들로 취소·조회할 수 있다. [Epic Gameplay Timers](https://dev.epicgames.com/documentation/en-us/unreal-engine/gameplay-timers-in-unreal-engine)

| 발생 계기 | 수행 작업 |
|---|---|
| 시전·소품 작동·손 해제 | 바뀐 수신기만 처리 큐에 추가 |
| 접촉 시작·종료·충돌 | 접촉 집합과 결합 갱신. 필요한 S4·표면 영향을 등록 |
| 효과 만료 | 가장 가까운 종료 시각을 예약하고, 깨어나면 이미 끝난 효과를 일괄 제거. 전체 Actor의 Tick에서 카운트다운하지 않음 |
| 지속 가열·바람·포집 | 활성 원천과 노출 대상에만 제한 주기의 타이머 적용. 실제 경과 시간을 사용하고 중간 만료 경계를 반영 |
| 원천 제거·대상 파괴 | 타이머·접촉·결합·지연 시전을 해제하고 약한 참조의 유효성을 검사 |
| 화면 남은 시간 | 서버 종료 시각과 보정된 서버 현재 시각으로 각 화면에서 계산. 매 프레임 남은 숫자를 네트워크 전송하지 않음 |

**[추천]** 이동·충돌·화면 애니메이션은 필요한 엔진 갱신을 계속 사용한다. 특히 활성 당김·바람의 힘은 이동 계산 주기에 적용할 수 있다. 피하려는 것은 모든 물체에서 매 프레임 6반응을 전수 검색하는 작업이다. 타이머 주기는 체감·CPU 측정 뒤 정하며 새 게임 규칙으로 고정하지 않는다.

## 3. 서버 판정과 화면 동기화

### 3.1 단일 사용·소비 요청

**[사실]** 언리얼 네트워크는 서버가 기준 상태를 관리하고 이를 클라이언트에 복제하는 구조다. RPC의 실행 위치는 Actor 소유권·연결 등에 영향을 받는다. [Epic Networking Overview](https://dev.epicgames.com/documentation/en-us/unreal-engine/networking-overview-for-unreal-engine), [Epic RPC](https://dev.epicgames.com/documentation/unreal-engine/remote-procedure-calls-in-unreal-engine)

| 순서 | 서버 처리 | 보장할 결과 |
|---:|---|---|
| 1. 요청 | 소유한 Controller/Action Component에서 `RequestId`, `StackId`, 본 재고 개정, 조준 정보 전송. `RequestId = 접속 세대 ID + 증가 번호` | 다른 사람의 아이템 Actor에 직접 서버 RPC를 보내는 구조를 피함 |
| 2. 중복 확인 | 같은 ID·같은 내용은 기존 처리 상태/결과 반환. 같은 ID·다른 내용은 거부 | 응답 유실 뒤 재전송되어도 다시 소비·발동하지 않음 |
| 3. 유효성 검사 | 연결 소유권·아이템 실재·수량·예약·현재 행동 가능 상태·허용 문장 검사 | 위조·없는 재고·충돌한 예약은 거부하고 소비하지 않음. 도안 생성 권한과 완제품 사용 권한 검사는 분리 |
| 4. 찢기 확정 | 서버의 한 처리 구간에서 수량 1 감소 + `ActionId`·`EventId` 발급 + 문장·도안 버전·대상 잠금 + 처리 결과 기록 | 검사와 소비 사이에 지연 작업을 끼우지 않음. 실제 대상 없음·고정체 같은 문장 결과는 여기서 소비를 되돌리는 사유가 아님 |
| 5. 준비·발동 | 승인 시 계산한 준비시간 뒤 잠근 대상·표면을 검사하고 실행. 결과 없음도 같은 사건의 결과로 기록 | 그 사이 대상 소멸·사거리 이탈이면 재선택하지 않으며 두 번째 소비도 하지 않음 |
| 6. 전달 | 요청자에게 승인/거부 결과, 관련 화면에 재고·활성 상태·원인 요약 전달 | 응답과 상태 복제 도착 순서가 달라도 ID·개정 번호로 맞춤 |

요청에는 원하는 행동과 조준 후보만 담고 문장·수량·봉인·소유자는 서버 재고에서 읽는다. 수량 변경을 확정하기 전에 Blueprint 이벤트나 비동기 작업을 호출해 같은 거래에 다시 진입하지 않는다. 요청 입구의 Actor와 Component는 복제를 설정한다. RPC 자체의 반환값을 기다리는 방식이 아니라 별도 응답 메시지에 `RequestId`를 실어 결과를 맞춘다.

| 경쟁 상황 | 처리 원칙 |
|---|---|
| 수량 1개에 서로 다른 요청 두 개 | 서버 큐에서 먼저 승인된 요청만 소비. 다음 요청은 최신 수량으로 거부 |
| 연타로 새 요청 ID를 계속 만듦 | 중복 ID 검사만으로 막을 수 없음. 진행 중 행동의 허용 상태와 서버 요청량 제한도 검사. 신규 게임 쿨다운을 임의 추가하지 않음 |
| 같은 월드 물품 동시 줍기 | `StackId`의 컨테이너 이전을 한 거래로 처리. 먼저 승인된 한 사람에게만 이전 |
| 제작 완료·취소 동시 도착 | `ActionId`의 상태 전이를 한 번 확정. 완료가 먼저 확정됐으면 늦은 취소가 제품·재료를 되돌리지 않음 |
| 중복 결과 캐시 정리 | 최근 결과와 수신 번호 구간을 보관. 캐시 밖의 오래된 ID는 새 요청으로 재실행하지 않고 만료 응답·현재 상태 재조회로 처리 |
| 접속을 새로 연결 | 서버가 새 접속 세대 ID를 발급. 이전 세대 요청 재생 금지. 실제 진행 복구 여부는 T1 정책을 받음 |

**[추천] 보장 범위:** 살아 있는 같은 서버 세션에서 승인된 작업의 효과·소비는 최대 한 번 적용하고 같은 요청 결과를 되돌려준다. 영구적인 통신 단절에서는 요청 도달·응답 자체를 보장할 수 없다. 호스트 프로세스 종료를 넘어선 단일 처리는 5장의 저장 정책·복구 구현이 필요하므로 스파이크 1의 보장이라고 쓰지 않는다.

정상 거부·중복·오래된 상태는 결과 코드로 응답한다. 네트워크 검증 실패와 소비 후 발생한 문장 실패를 같은 오류로 묶지 않는다.

**[사실]** `WithValidation`을 사용하는 Server RPC의 검증 실패는 해당 클라이언트의 연결 해제로 이어진다. [Epic RPC 검증](https://dev.epicgames.com/documentation/unreal-engine/remote-procedure-calls-in-unreal-engine) **[추천]** 정상적인 대상 없음·연타·낡은 재고 상태를 이 검증 실패로 처리하지 않는다.

### 3.2 대상 잠금과 권위

| 대상·결과 | 서버 기준 자료 | 화면 표현과 경계 |
|---|---|---|
| 조준 | 클라이언트 조준점은 후보. 서버가 시전자 기준 거리·시선·대상 종류·차폐를 검증 | 입력 직후 조준·준비 표현은 가능. 대상 적중·상태 변화는 승인으로 확정 |
| 너·물건·나 | 찢기 시 `TargetEntityId`와 부위/부착점 잠금. 너는 동료·몬스터 공통 경로 | 지연 중에도 같은 대상을 따라감. 소멸·범위 이탈 시 자동으로 옆 대상을 고르지 않음 |
| 바닥·벽 | 찢기 시 표면 ID·국소 도장 위치·법선·연결 범위 잠금 | 표면 효과 구역을 표시. 근처 사람 몸에 직접 도장을 추가하지 않음 |
| 주변 | `TargetPolicy=AreaAtActivation`을 별도 표현. 발동 순간 시전자 중심과 노출 검사를 사용하고 그 결과를 확정 | 이후 시전자를 따라다니는 오라가 아님. 일반 단일 대상 잠금과 같은 필드로 구현하지 않음. 지연 중심/목록은 §8.2 확정 기준 적용 |
| 넓게 | 원래 중심 대상/표면을 보관하고 확장 선택 정책으로 후보를 계산 | 동료·몬스터를 진영으로 임의 제외하지 않음. 벽 차폐·연결 표면 기준 유지 |
| 당김 | 찢기 승인 시 시전자 위치를 고정 기준점으로 보관. 지연 뒤 거리도 그 점에서 검사하며 이후 시전자 이동을 따라가지 않음 | 힘·고정·막힘 결과 표시. 고정 면 대상은 벽 파괴·시전자 대체 이동 없음. 나 대상은 준비 중 움직였으면 자신의 기준점으로 당겨질 수 있음 |
| 접착·반발·상태 | 서버 반응 처리 결과가 최종 상태 | 재질·소리·빛은 그 상태를 읽어 각 화면에서 구성 |

**[추천]** `FLockedCastTarget`에 대상 선택 정책, 잠금 시각, 발동 시각, 대상/표면 키, 고정 기준점, 발동 시 확정된 대상 목록을 나누어 둔다. 규칙 해석이 바뀌어도 필드 의미를 바꾸지 않고 선택 정책만 교체하도록 한다.

### 3.3 이동과 지속 상태 복제

**[사실]** `CharacterMovementComponent`는 네트워크 역할별 이동·예측·서버 보정 흐름을 제공한다. 별도 위치 변경을 추가할 때 이 흐름과 맞추어야 한다. [Epic Networked Movement](https://dev.epicgames.com/documentation/unreal-engine/understanding-networked-movement-in-the-character-movement-component-for-unreal-engine)

| 대상 | 구현 방향 | 주의점 |
|---|---|---|
| 사람·Character 기반 생물 | `UScrollCharacterMovementComponent`에 승인된 외력·접착 제약을 입력. 당김은 고정 기준점, 반발은 승인 충돌, 접착은 결합 자료로 처리 | 일반 이동은 기존 예측 유지. 외력 예측을 추가하면 서버 상태를 입력 이력에 연결해 재실행 때도 같은 효과 ID를 사용 |
| 고정 소품·벽 | 고정 성질로 이동 거부, 힘과 막힘 원인만 기록 | 서버에서 다른 이동 효과로 대체하지 않음 |
| 제한 운반물 | 서버가 정한 충돌체·질량·이동 결과를 복제하고 원격 화면은 보간 | 처음에는 제한된 운반물만 사용. 임의 물리 물체의 완전한 동기화를 약속하지 않음 |
| 바닥 효과·접착 결합 | 구역·막 ID·대상 쌍·종료 시각·개정 번호 복제 | 결합 상대 Actor가 아직 도착하지 않았으면 해결 대기. 사라지면 제약을 해제하며 영구 이동 잠금 금지 |
| 재고 | 해당 컨테이너를 볼 권한이 있는 화면에 묶음별 상태·개정 번호 전달 | 실제 권한은 T1 결정. 클라이언트는 수량 원본을 직접 수정하지 않음 |
| 지속 효과 | 효과 ID·속성·세기·시작/종료 시각·원인 ID의 현재 목록 전달 | 일회성 Multicast만으로 지속 상태를 유지하지 않음. 관련성 밖에서 돌아와도 현재 목록으로 재구성 |
| 짧은 연출 | 사건 ID가 붙은 표현 통지와 지속 상태를 분리 | 통지가 유실돼도 최종 상태가 맞아야 함. 같은 사건의 효과음·카메라 표현을 중복 재생하지 않음 |

**[추천]** 스파이크는 일반 복제 배열과 명시적인 개정 번호로 시작한다. 변경량이 실제 병목이면 변경 항목만 보내는 방식으로 바꾼다. 최적화 방식보다 ID·소유 범위·상태 일관성을 먼저 고정한다.

당김의 구현 후보는 CharacterMovement의 Root Motion Source 또는 특수 이동 경로다. 서버의 직접 위치 변경만으로 마무리하지 않고 소유 클라이언트의 승인 명령 적용·예측·보정을 함께 검사한다. 접착 중에도 시점·사용·손 해제에 필요한 입력을 유지하며, 해제 뒤에는 현재 바닥·낙하 조건으로 이동 모드를 결정한다. 오래전에 저장한 이동 모드로 무조건 돌아가지 않는다.

### 3.4 리슨 서버 체감과 지연 검사

| 호스트·클라이언트 차이를 줄이는 방법 | 적용 경계 |
|---|---|
| 공통 요청 경로 | 호스트도 같은 승인 함수·수량 검사·사건 기록을 거침. 로컬 호스트만 별도로 수량을 먼저 줄이지 않음 |
| 즉시 가능한 로컬 반응 | 입력·조준·손 준비·요청 대기 표현. 확정 소비·상대 이동·접착 해제 성공을 미리 영구 반영하지 않음 |
| 예측 취소·승인 합치기 | 로컬 임시 표현에 `RequestId`, 승인 후 `ActionId` 연결. 거부되면 임시 표현을 종료하고 서버 수량·상태로 맞춤 |
| 같은 시간 기준 | 서버 종료 시각 기준으로 남은 시간을 계산. 늦게 받은 화면도 수신 순간부터 전체 지속을 다시 시작하지 않음 |
| 화면 갱신 입구 | 서버가 값을 쓴 뒤 호스트 표현 갱신, 원격 복제 알림 뒤 클라이언트 표현 갱신이 같은 읽기 함수를 사용 |
| 과도한 신뢰 전송 방지 | 찢기·완료·취소 같은 드문 요청만 Reliable 후보. 매 프레임 조준·효과음을 Reliable RPC로 쌓지 않음 |

**[사실]** `AGameStateBase::GetServerWorldTimeSeconds`는 서버와 클라이언트에 동기화한 서버 시각을 제공한다. [Epic GameMode·GameState](https://dev.epicgames.com/documentation/unreal-engine/game-mode-and-game-state-in-unreal-engine) **[추천]** 효과 시간의 기준으로 이를 사용하되, 실제 만료 판정은 서버만 수행한다. 지연 때문에 생기는 호스트의 우위를 완전히 없앤다는 보장은 하지 않는다.

**[사실]** Epic은 네트워크 에뮬레이션으로 지연·손실 등 불리한 조건을 모사하는 기능을 설명한다. RPC·복제 자료의 순서는 적용 범위에 제약이 있으므로 서로 다른 Actor와 개별 알림이 항상 한 순서로 도착한다고 가정할 수 없다. [Epic Network Emulation](https://dev.epicgames.com/documentation/unreal-engine/using-network-emulation-in-unreal-engine), [Epic Replicated Object Execution Order](https://dev.epicgames.com/documentation/unreal-engine/replicated-object-execution-order-in-unreal-engine)

| 검사 | 기록할 증거·통과 조건 |
|---|---|
| 정상망 → 지연 → 손실 → 혼합 | 실제 설정값·왕복시간·손실률·빌드·회차 ID 기록. 검사 시작안은 왕복 0/100/200ms와 손실 0/1/5%의 일부 조합이며 게임 수치가 아님. 도구 설정이 단방향인지 왕복인지 확인 |
| 동시 줍기·수량 1 연타·중복 재전송 | 요청/작업 ID별 소비 횟수·획득 수량. 승인 작업당 한 번, 거부 작업은 0번 |
| S6→S2·중첩 만료 | 같은 상태 개정에서 물기·잔여 열·접착·효과 종료가 일치. 약한 재시전으로 강한 효과 시간이 늘어나지 않음 |
| 지연 발동 직전 이동·소멸 | 대상 재선택 없음, 한 번 소비, 이유 결과 도착 |
| 이동·손 해제 | 접착/반발/당김 상태가 최종 수렴하고 제약 종료 뒤 모든 화면에서 이동 가능. 최대 보정 거리·정착 시간도 측정해 T2와 체감 기준 결정 |
| 다른 Actor의 복제 순서 뒤바뀜 | 결합·원인 자료가 늦어도 잘못된 상대에게 붙거나 효과를 다시 실행하지 않음 |
| 관련성 이탈·복귀·재접속 시도 | 재전송 연출 없이 현재 상태를 재구성. 재접속 정책이 없는 스파이크에서는 실패도 기술 기록에 남김 |
| 호스트 종료 | 정상 실험 중단으로 기록. 호스트 이전·복구 성공으로 처리하지 않음 |

0ms 조건은 검사 기준점이지 실제 인터넷의 보장값이 아니다. 연결 복구 후의 상태 수렴 허용 시간과 이동 보정 체감 목표는 첫 패키지 측정 뒤 정한다. 2인·4인 결과, 호스트·원격 플레이어 결과, 재미 회차·기술 검사를 나누어 기록한다.

|---|---|
| 필드 추가·자료형 변경 | v1→v2→v3처럼 작은 순차 변환. 누락 필드의 기본값은 변환 단계에 명시하고 예전 저장 표본으로 재검사 |

| 알 수 없는 필수 ID | 조용히 삭제·무료 대체 지급하지 않음. 원본 유지, 읽기 실패 사유 또는 격리 자료를 반환하고 콘텐츠 담당에게 확인 |
| 지원하지 않는 미래 버전 | 자동 하향 변환·덮어쓰기 금지. 지원 범위를 표시 |
| 쓰기 실패·손상 | 마지막 정상 세대를 보존하고 새 세대의 쓰기·읽기 검증 뒤 채택. 실패 확인 시 두 공간 공동 중단, 현 메모리 상태 재시도와 이전 정상본 복구 경로 시험 |
| 서버 시각이 재시작됨 | 중간 효과 저장이 승인될 경우 남은 기간·원천 상태를 저장하고 복원 시 새 서버 시각으로 환산. 이전 월드의 절대 종료 시각을 그대로 사용하지 않음 |
| 연결 대상이 바뀜 | 영구 ID로 다시 연결. Actor 포인터·임시 네트워크 식별자·에셋 메모리 주소를 저장하지 않음 |

마지막 정상본 보존·변환·일관된 거래 복원은 **프로젝트가 구현하고 검사할 기능**이다. `USaveGame`이나 비동기 저장 API만으로 자동 보장되는 것으로 쓰지 않는다. 저장 실패 안내 표현은 T2, 재개 규칙은 T1 §5·§7을 따른다.

### 5.3 저장 실패의 공동 중단과 재개

[추천·v2.2 적용] 디스크 실패를 확인하면 공방·던전의 물때·효과·공정·새 거래 승인을 함께 멈춘다. 실패 알림만 띄우고 정산을 계속하는 경로를 만들지 않는다.

| 단계 | 구현 후보·검사할 계약 |
|---|---|
| 실패 확인 | 공유 중단 상태와 마지막 정상 세대 기록. 이미 확정한 거래는 환불·재실행하지 않음 |
| 진행 중단 | 게임 진행용 타이머/예약 실행을 막고 남은 시간을 같은 시점으로 보관. 물때·효과·공정 콜백도 중단 상태 검사. UI·연결 안내·디스크 재시도는 가능해야 함 |
| 승인 전 요청 | 새 거래 보류/거부 결과 전달. 승인·수량 감소·제품·성공 표현 없음 |
| 재시도 | 현 메모리의 공동 개정으로 스냅샷 생성. 자금·재고·거래/보상 번호·작업·원정 자료 함께 확인 |
| 성공 후 재개 | 정상 저장 세대·공동 개정 확인 뒤 남은 시간으로 타이머 재예약·재개. 중단된 벽시계 시간으로 물때/효과/공정을 뒤늦게 실행하지 않음. 이후 개인 기록 전달 |
| 계속 실패·강제 종료 | 마지막 정상 시점과 미보존 구간 안내. 정상 종료 재시도 또는 마지막 정상본 복구 선택. 강제 종료 뒤 최신 메모리 보존을 약속하지 않음 |

호스트 정상 종료도 두 공간 공동 저장·중단이며 비정상 종료는 마지막 정상 공동 세대다. 개인 전달은 그 호스트 세대에 남은 사건 ID로 재시도한다. 중단·재예약 타이머, 오래된 완료 콜백, 손상 시 이전 정상본 복구는 본편 저장 검사에서 확인한다.

## 6. 콘텐츠를 늘리는 방법

### 6.1 표를 채워 늘릴 수 있는 범위

| 콘텐츠 표 | 추가할 열·참조 | 표만으로 가능한 범위 | 새 구현이 필요한 경계 |

복잡한 조건 목록은 긴 문자열 한 칸에 넣지 않고 부모 ID를 가진 별도 행으로 둔다. T0의 재료 약 20종·의뢰 약 40건 등은 크기를 가늠하는 입력일 뿐 고정 한도로 쓰지 않는다. 모든 새 AI·레벨·퍼즐까지 표만으로 만들 수 있다고 약속하지 않는다.

### 6.3 후기·신문 문장 틀

**[사실]** String Table은 문구를 키로 참조하는 기능이며, `FText::Format`은 이름 붙은 인자를 문장 틀에 넣을 수 있다. [Epic String Tables](https://dev.epicgames.com/documentation/en-us/unreal-engine/using-string-tables-for-text-in-unreal-engine), [Epic Text Localization](https://dev.epicgames.com/documentation/en-us/unreal-engine/text-localization-in-unreal-engine)

| 자료 | 권장 형태 |
|---|---|
| 틀 정의 | `TemplateId`, `TemplateVersion`, 후기/신문 종류, 조건 판정 ID, 필요한 사건 종류·결과, `StringTableKey`, 허용 인자 이름·자료형 |
| 사용 인자 | 효과명·대상명·수량·지역 ID·문장·행위자·제조자 등 **기록이 제공하는 값만** 허용 |
| 생성 결과 | `PublicationId`, 고른 틀 ID·버전, 인자 값, 근거 사건/납품 ID, 생성된 날짜·정책 버전 |
| 생성 위치 | 서버가 조건을 평가하고 틀·인자를 확정. 각 화면은 같은 자료를 받아 현지화된 문장으로 표시 |
| 과거 기사 재현 | 사용한 틀 버전을 보존하거나 발행 당시 완성 문구도 함께 보관. 재접속 때 틀을 다시 뽑지 않음 |
| 문장 품질 | 완성 문장 단위의 틀을 T6가 작성. 조사·이름·수량의 극단 사례를 미리보기로 확인 |

반복 제한·선택 우선순위·신문 발행 주기·기사 수·말투·내용은 T6가 정한다. 난수로 허구의 사고·평판 하락을 생성하지 않는다. 사건 인과의 누락은 빈 값을 억지로 끼우기보다 해당 틀을 선택 불가로 처리한다.

계획은 경고이고 실제 예약만 물품 중복 소비를 차단한다. 일시 단절·호스트 중단은 진행 중 작업/예약을 저장하며, 명시적 작업 취소와 구별한다. 중간 저장은 두 공간·준비 중 발동·잔여 물때·소비/보상 번호를 같은 스냅샷으로 복구한다. 개인 기록은 호스트 저장 성공 뒤 사건 ID로 전달한다. 영속 저장 실패 시 두 공간 공동 중단·재시도, 검증한 공동 시점의 성공 뒤 재개한다.

공동 발견은 사건 시점 아직 던전에 참여 중인 출발자이며 직접 해독자는 별도다. 참여가 유지된 일시 단절자는 공동 참여로 기록할 수 있으나 화면을 실제로 봤다고 표시하지 않는다.90초 자리 예약 만료와 그 원정 물때 종료의 참여 종료를 혼동하지 않는다. 먼저 귀환자는 공동 도감만 갱신한다.

스파이크1에서는 상태/소비/원인·손 해제와2초 보호만 확인하고, 주문/개인 영구 저장/고객/경제를 한꺼번에 구현하지 않는다. 스파이크2와 슬라이스에서 예약 충돌·고객 소비·기록 재전달·종료 복원을 확인한다. 수급·재부여 시간·저장 간격·작업일은 검증 전 시작값이다.
